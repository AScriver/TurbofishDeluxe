On this machine, WindowsSandbox.exe was absent on 2026-10-08. No sandbox feature was installed or enabled, no original process was attached, and no retail saves/registry were changed. ## AppContainer candidate, unperformed

Official Windows documentation supports [AppContainer for unpackaged legacy apps](https://learn.microsoft.com/en-us/windows/win32/secauthz/appcontainer-for-legacy-applications-). Its token/capabilities provide isolation beyond low integrity; documentation describes selective file/registry virtualization, but does not establish this game's exact HKCU/CommonAppData results. [Profile creation](https://learn.microsoft.com/en-us/windows/win32/api/userenv/nf-userenv-createappcontainerprofile) creates Windows-managed user storage outside project scratch. Any experiment must identify that footprint and its cleanup explicitly. No profile/token/ACL/controller was created in this investigation.

A candidate controller would own a unique disposable profile, private copied executable/assets and a no-breakaway, kill-on-close [job](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects). It would start suspended with security capabilities, verify the actual child token/job before resuming, grant access only on private fixtures/copies and have no ordinary-process fallback. A synthetic program must first exercise known folders/registry/child containment and HWND capture under that exact policy. Denied calls are failures to investigate, never permission to broaden access to retail data. Profile deletion and process cleanup need actual receipts.

[Job UI restrictions](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-jobobject_basic_ui_restrictions) cover ChangeDisplaySettings and mutating SystemParametersInfo. W1 `SexyAppFramework/DDInterface.cpp:440–444` also uses DirectDraw exclusive [SetDisplayMode](https://learn.microsoft.com/en-us/windows/win32/api/ddraw/nf-ddraw-idirectdraw7-setdisplaymode); the job documentation does not prove that route blocked. Binary-confirmed windowed startup or separately verified denial is required before retail launch. This remains a proposed route, with GUI/DirectDraw compatibility and exact state isolation **not tested**.

The earlier mixer concern is refined: Microsoft's [legacy mixer documentation](https://learn.microsoft.com/en-us/windows/win32/multimedia/audio-mixers-in-windows-vista) says Vista-and-later volume/mute controls affect the calling process's audio session, not other applications or hardware. W1's mixer restore alone therefore does not establish a global-volume side effect on this machine. Other retail BASS calls and session behavior remain unknown. No original process was launched to resolve them.
