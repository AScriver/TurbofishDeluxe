# Tracker music feasibility (2026-10-09)

This is a design and local feasibility record, not a runtime feature or an audible fidelity claim. The main crate still forbids unsafe Rust and plays effects only. Installed MO3 files are read in place. Pinned WinFish W1 (`f919b3c241cfd611c547f1653fb3514f500f761b`) supplies secondary music-call expectations; the installed game has not been run for comparison. Pinned PopLib P2 (`45776cefdeb8cd5bd43ce7f345aa7be1807c7380`) `PopLib/audio/{openmptmusicinterface,musicinterface}.{cpp,hpp}` was studied for order-based decoding and ownership, not reused.

## Original isolated binding candidate (2026-10-09)

The reviewed lineage is an **original, separate Rust crate** in ignored `.scratch/audio-binding-probe-01/crate`, using only the [official libopenmpt 0.8.9 C header](https://lib.openmpt.org/files/libopenmpt/dev/libopenmpt-0.8.9+release.dev.windows.vs2022.zip) (`inc/libopenmpt/libopenmpt.h`) for ABI signatures and ownership rules. No code from `openmpt 0.3.1`, `openmpt-sys 0.1.0`, WinFish, or PopLib was copied into the binding. The binding's own `LICENSE` is BSD-3-Clause with Turbofish Deluxe contributors as copyright holders; official libopenmpt and its DLL dependencies retain their separate notices in the native archive. The independent review in ignored `.scratch/architecture-audio-license/review-binding.md` found no caller-accessible Rust memory-safety defect for source SHA-256 `D82AE485D9CC7F13BB6318F253EB536C45214DB92440562D4FCDA6FA9A4DA1FB`, assuming the pinned DLL obeys its C contract; maintained adoption and distribution still require review. No main dependency or unsafe policy changed.

The module wrapper accepts borrowed bytes, uses libopenmpt's exported silent logging and store-error callbacks with null userdata, copies every returned UTF-8 error string before freeing it with `openmpt_free_string`, and destroys the non-null native module once in `Drop`. It has no Rust callback or temporary C string whose lifetime extends into rendering. Each native module operation clears stale stored errors, checks the result and new stored error, and validates positive order counts, exact order/row seek readback, repeat acceptance, 8–192 kHz stereo sample rate, even buffer length, a 16,384-frame maximum request, returned frame bounds, and finite PCM. `Module` is deliberately neither `Send` nor `Sync`; construct and retain it inside one decoder thread. Unsafe operations live only in the private binding, under `deny(unsafe_op_in_unsafe_fn)`; the game crate can keep `unsafe_code = "forbid"` when consuming a separately reviewed safe API. Native DLL loading, ABI trust, decoder safety, package distribution, and callback/device behavior still need review; a safe Rust surface does not make the DLL safe by itself.

The probe links the official VS2022 x64 `lib/amd64/libopenmpt.lib` directly with a private `build.rs` search path. Its first decode-only test used a process-local native DLL path; the later bounded output test copied the **complete five-DLL set beside its private executable**, checked every hash before launch, and confirmed all five actual loaded module paths and hashes while the process was live. It uses a private Cargo target and ignored storage, no system installation and no copied music. The earlier wrapper probe remains evidence that the native package decodes these files, but it is **not the adoption choice**: `openmpt 0.3.1` has an unresolved missing BSD-Attribution text in its published archive, and `openmpt-sys 0.1.0` has no declared license or package notice. A later `openmpt-sys` declaration for apparently identical code is useful lineage evidence but does not supply the missing notice in the 0.1.0 package. The new binding has no dependency on either crate.

### Selected native startup contract

The pinned official native package is a **mandatory runtime prerequisite** for this link-time binding. A future documented Windows launcher/build helper must verify the archive, import library and all five DLL hashes, copy those five DLLs beside the owned executable, and diagnose a missing/mismatched file **before launching** the game. Do not promise an in-game fallback when a load-time DLL is absent: Windows can fail before Rust `main` starts. Once the process has loaded the pinned set, module decode and output-device failures may use the proposed nonfatal music-unavailable path. This selection avoids a speculative dynamic-loading abstraction, but the actual maintained launcher and package notices have not yet been implemented. The private output helper `.scratch/audio-binding-probe-01/run-output-probe.ps1` demonstrates the prerequisite and audits loaded paths without modifying the system DLL search path.

## Earlier wrapper and output feasibility probes

The historical `openmpt = 0.3.1` probe decoded the user's installed MO3 bytes to bounded, initialized stereo `f32` buffers at 48 kHz. It linked the official Windows VS2022 x64 libopenmpt 0.8.9 import library. `rodio = 0.22.2` with `default-features = false, features = ["playback"]` sent those samples to the default device through `DeviceSinkBuilder`, `Player`, and `SamplesBuffer`. Its locked playback-only graph includes CPAL 0.17.3 and no rodio codecs or recording feature. [Rodio's 0.22.2 feature manifest](https://docs.rs/crate/rodio/0.22.2/source/Cargo.toml), [device API](https://docs.rs/rodio/0.22.2/rodio/stream/struct.DeviceSinkBuilder.html), [player API](https://docs.rs/rodio/0.22.2/rodio/struct.Player.html), and [sample-buffer API](https://docs.rs/rodio/0.22.2/rodio/buffer/struct.SamplesBuffer.html) are the versioned output API references. No main dependency has been adopted.

The eventual music owner should keep the device sink and player alive, and construct each decoder module inside its own task because the module holds a native pointer. Route a requested track/order through a small command channel; seek the module by order and row zero, check the resulting current order, and send initialized PCM blocks through a bounded queue. Keep at most two short blocks pending, discard stale blocks on order change, and account for intentional silence/end versus queue starvation. The app owns play/pause, track transition and local player volume; the decoder owns module lifetime. A dedicated music player avoids changing the current effects path. The original-binding output probe tested continuous two-block scheduling, one 0→12 transition, pause/resume and clean stop for about 2.4 seconds; long-term underrun behavior, loop boundaries and actual-game transitions remain unverified.

`openmpt 0.3.1`'s published `Module::create_from_memory` takes `&mut Vec<u8>` and returns only `Result<Module, ()>`. Its stereo render implementation requests **half the Vec capacity**, not half its length; callers using that older probe must initialize full capacity, bound returned frames, and inspect only that many samples. It does not enforce sample rate or report detailed load errors. The original binding instead renders through the exact provided `&mut [f32]` length, accepts borrowed input bytes, reports native load errors, and validates order/row readback. Neither probe proves decoder safety against malicious modules. Keep the main `unsafe_code = "forbid"`; direct C-symbol FFI in that crate is rejected.

After successful native loader startup, if the module decoder or output device cannot initialize, show a nonfatal music-unavailable diagnostic and continue the game without tracker music. Missing native DLLs must instead be diagnosed by the launcher before the game starts. Do not invoke the original executable, silently use a different track, or commit converted proprietary audio. This fallback is a proposed runtime policy, not implemented. Local conversion to WAV is not selected: it adds generated install-derived files and does not solve startup transitions or loop handling.

## Executed checks and limits

All scripts were parser- and automatic-variable-validated through `Invoke-CodexPowerShell.ps1`; Cargo used ignored, private `CARGO_HOME` and `CARGO_TARGET_DIR`. The first decode probe (`.scratch/audio-probe-01/crate/src/main.rs`) compiled and loaded all three owned MO3 files. It checked order bounds, readback and finite nonzero PCM at `Insaniq2` orders 0/12/25/37, `Alien` 0/1/3 and `Lullaby` 0; invalid bytes returned an error in its focused test. Owned file hashes and exact measurements remain in the ignored probe output. Its first compile failed because the published wrapper requires `&mut Vec<u8>`; corrected and passed.

The second output probe (`.scratch/audio-output-probe-01/crate/src/main.rs`) used only owned `Insaniq2` order 0 then order 12. It rendered two 38,400-frame stereo blocks at 48 kHz, each with 76,800 nonzero finite samples, opened the default device, applied local player gain 0.05, and kept one queued item. Process PID 11224 exited after 989.7891 ms. Position advanced to 325 ms; while paused for 200 ms it changed from 325 to 330 ms; after a bounded stop/drain and order seek the second position reached 295 ms. Output callback errors were zero, the final queue emptied, and the process exited 0. `Player::stop()` is asynchronous: an immediate-empty assertion failed in the first runtime attempt; source review and a bounded drain resolved it. The initial output build had a separate channel-count type error (`NonZero<u16>` required), corrected before the runtime checks. Rodio's expected sink-drop notice appeared at shutdown. No owned probe process remained, and `.scratch/` is ignored.

The callback count and position prove API progress on this host, not audible fidelity, low-latency reliability, absence of glitches, or exact source mixing. No loopback capture, sound-device selection or system volume/settings change, full track loop, fade, concurrent effects, pause/resume of the actual game, or normal-speed visible playtest was performed. No original executable, original save or installed file was changed.

The original binding probe used `.scratch/audio-binding-probe-01/run-binding-tests.ps1`, validated and executed through `Invoke-CodexPowerShell.ps1`, with its own `CARGO_HOME`, `CARGO_TARGET_DIR`, import-library search path, and process-local native DLL path. On Rust 1.95.0 MSVC, `cargo test --offline` passed two integration tests: invalid/empty module diagnostics, invalid rate/odd/oversized/zero buffers, bounded slice writes, repeat control, invalid order/row, and all eight requested orders of the three installed MO3 files. Each order returned finite nonzero stereo PCM; `Lullaby` order 0 first became nonzero after 131,072 frames, so the original four-block test failed and was corrected to allow up to thirty bounded blocks. The first crate compile failed on a moved Rust `Option<String>`; a narrow ownership fix resolved it. `cargo fmt --check` and `cargo clippy --offline --all-targets -- -D warnings` then passed in the private crate. No output device was opened for this binding probe, and there was no main-crate build or integration. These checks establish ABI linkage and bounded decoding for the owned files on this host, not continuous playback, malicious-input safety, retail mixing, or fidelity.

The subsequent `.scratch/audio-binding-probe-01/run-output-probe.ps1` was parser/automatic-variable validated before execution. It verified archive SHA-256 `A23E375E576E3A6997FFEEB6CF34488E9020E2A5D8226856B02628B6A87C5E8E` and import library SHA-256 `537758E3D065281E887C0D3310BE471FCB322DE82F74F5DF969624D7A16156CF`, built a new locked/offline `rodio 0.22.2` probe with a private target, verified and copied the five tabled DLLs beside `.scratch/audio-binding-probe-01/output-target/debug/turbofish_audio_binding_output_probe.exe`, and checked their hashes again. While PID 35972 was live, PowerShell's loaded-module view returned **all five** DLL paths in that exact executable directory, each with the matching tabled SHA-256; no package DLL resolved from PATH, a system directory or the original game. The owned process exited 0 and was absent on cleanup. No system DLL/device setting, installed game file, original process, or converted music was touched.

The output process decoded `Insaniq2.mo3` through the original binding, used `rodio` at 48 kHz and player-local gain 0.05, kept at most two 4,096-frame stereo blocks queued, paused for 200 ms (reported in-block position 55→60 ms), drained one old queued block, sought order 12 with readback, and drained two final queued blocks. It consumed 12 blocks before transition and 10 after; totals were 25 rendered blocks, 102,400 frames and 204,800 nonzero samples, with maximum queue 2, zero reported queue underruns, render errors and output callback errors, and 2.399-second process runtime. This is a bounded output-device/API result, not audible comparison or a long-run underrun guarantee. The first output attempt incorrectly required `Player::get_pos()` to exceed 700 ms; short `SamplesBuffer` items reset that position per item, and it reported 65 ms after multiple buffers. Counting consumed blocks instead preserved the intended progress test and passed. Rodio emitted its ordinary sink-drop notice on clean exit. Full track loops, sustained playback, real game transitions and human listening remain untested.
