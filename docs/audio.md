# Tracker music integration and checks (2026-10-09)

This records the A24 tracker playback implementation, its coordinated native runtime checks, and earlier isolated feasibility work. The maintained executable has run unmuted with cue, queue, pause, and DLL-load evidence; no human listening comparison or retail execution established audible fidelity. The main crate still forbids unsafe Rust; the separate reviewed binding owns the C boundary. Installed MO3 files are read in place. Pinned WinFish W1 (`f919b3c241cfd611c547f1653fb3514f500f761b`) supplies secondary music-call expectations. Pinned PopLib P2 (`45776cefdeb8cd5bd43ce7f345aa7be1807c7380`) `PopLib/audio/{openmptmusicinterface,musicinterface}.{cpp,hpp}` was studied for order-based decoding and ownership, not reused.

## Maintained A24 integration

`crates/turbofish-openmpt` carries the reviewed original binding source with SHA-256 `D82AE485D9CC7F13BB6318F253EB536C45214DB92440562D4FCDA6FA9A4DA1FB` and its own BSD-3-Clause notice. `src/music.rs` constructs the non-`Send` module in a dedicated output thread. A bounded control channel carries ordered atomic cue/pause states after each active fixed step, including the one-update alien warning. A separate bounded effect channel cannot block those states; a stop flag takes priority over the queues. Each worker pass renders at most two blocks, and queued tracker PCM remains bounded to two 4,096-frame stereo blocks. Order changes silence, stop and drain the old music player before seeking. Effects use up to 32 independent short-lived players and their own gain; overload drops an effect with a report. Telemetry has a bounded queue and reports dropped records. `--mute` skips the owner. Device and module errors report a visible music-unavailable diagnostic; module errors leave effects available, while one invalid effect reports only an effect failure. No converted music is retained. Cue/requested-order/queue/underrun/error reports enter the existing local evidence JSONL. Actual order advancement is not reported by the queue counter.

`scripts/Start-TurbofishDeluxe.ps1` downloads or uses a cached official 0.8.9 VS2022 archive in ignored `.scratch/native/libopenmpt-0.8.9`, verifies the pinned archive, import library and all five DLL hashes below, sets `OPENMPT_LIB_DIR`, builds with `cargo build --locked`, copies and rechecks the complete DLL set beside the owned executable, places official package notices beside it, and then launches the owned game. `-Offline -NativePackageDirectory <verified extracted package>` supports a previously acquired archive; this path checks the individual native files and notices but cannot attest the absent archive. `-PreflightOnly` verifies without building; `-PrepareOnly` builds and stages without launching. The native package is mandatory: a DLL loader failure can precede Rust startup, so only errors after successful loading have an in-game fallback. A debug/release executable moved without its five DLLs and notices is not a complete deployment.

The first Cargo graph attempt retained macroquad's `audio` feature and added rodio playback. `cargo metadata --format-version 1` failed because `quad-snd` and CPAL each transitively declare an ALSA `links` package. A target-specific Windows rodio dependency did not resolve it. Only `src/app.rs` used macroquad audio, so A24 removes that feature and routes its existing WAV-converted AU and OGG effect bytes through the same rodio 0.22.2 output owner (`playback`, `vorbis`, `wav`). The event-to-effect IDs and per-effect gain remain; the sound bytes are validated by rodio during presentation loading. This resolved the dependency graph, and Cargo.lock was updated by `cargo metadata`. The prior wrapper probe remains unadopted.

## Original isolated binding candidate (2026-10-09)

The reviewed lineage is an **original, separate Rust crate** first developed in ignored `.scratch/audio-binding-probe-01/crate`, using only the [official libopenmpt 0.8.9 C header](https://lib.openmpt.org/files/libopenmpt/dev/libopenmpt-0.8.9+release.dev.windows.vs2022.zip) (`inc/libopenmpt/libopenmpt.h`) for ABI signatures and ownership rules. No code from `openmpt 0.3.1`, `openmpt-sys 0.1.0`, WinFish, or PopLib was copied into the binding. The binding's own `LICENSE` is BSD-3-Clause with Turbofish Deluxe contributors as copyright holders; official libopenmpt and its DLL dependencies retain their separate notices in the native archive. The independent review in ignored `.scratch/architecture-audio-license/review-binding.md` found no caller-accessible Rust memory-safety defect for source SHA-256 `D82AE485D9CC7F13BB6318F253EB536C45214DB92440562D4FCDA6FA9A4DA1FB`, assuming the pinned DLL obeys its C contract. A24 adoption changed dependencies but retained the main crate's unsafe policy; distribution still requires notice and deployment review.

The module wrapper accepts borrowed bytes, uses libopenmpt's exported silent logging and store-error callbacks with null userdata, copies every returned UTF-8 error string before freeing it with `openmpt_free_string`, and destroys the non-null native module once in `Drop`. It has no Rust callback or temporary C string whose lifetime extends into rendering. Each native module operation clears stale stored errors, checks the result and new stored error, and validates positive order counts, exact order/row seek readback, repeat acceptance, 8–192 kHz stereo sample rate, even buffer length, a 16,384-frame maximum request, returned frame bounds, and finite PCM. `Module` is deliberately neither `Send` nor `Sync`; construct and retain it inside one decoder thread. Unsafe operations live only in the private binding, under `deny(unsafe_op_in_unsafe_fn)`; the game crate can keep `unsafe_code = "forbid"` when consuming a separately reviewed safe API. Native DLL loading, ABI trust, decoder safety, package distribution, and callback/device behavior still need review; a safe Rust surface does not make the DLL safe by itself.

The probe links the official VS2022 x64 `lib/amd64/libopenmpt.lib` directly with a private `build.rs` search path. Its first decode-only test used a process-local native DLL path; the later bounded output test copied the **complete five-DLL set beside its private executable**, checked every hash before launch, and confirmed all five actual loaded module paths and hashes while the process was live. It uses a private Cargo target and ignored storage, no system installation and no copied music. The earlier wrapper probe remains evidence that the native package decodes these files, but it is **not the adoption choice**: `openmpt 0.3.1` has an unresolved missing BSD-Attribution text in its published archive, and `openmpt-sys 0.1.0` has no declared license or package notice. A later `openmpt-sys` declaration for apparently identical code is useful lineage evidence but does not supply the missing notice in the 0.1.0 package. The new binding has no dependency on either crate.

## Earlier wrapper and output feasibility probes

The historical `openmpt = 0.3.1` probe decoded the user's installed MO3 bytes to bounded, initialized stereo `f32` buffers at 48 kHz. It linked the official Windows VS2022 x64 libopenmpt 0.8.9 import library. `rodio = 0.22.2` with `default-features = false, features = ["playback"]` sent those samples to the default device through `DeviceSinkBuilder`, `Player`, and `SamplesBuffer`. Its locked playback-only graph included CPAL 0.17.3 and no rodio codecs or recording feature. The A24 maintained graph adds `wav` and `vorbis` for installed effects. [Rodio's 0.22.2 feature manifest](https://docs.rs/crate/rodio/0.22.2/source/Cargo.toml), [device API](https://docs.rs/rodio/0.22.2/rodio/stream/struct.DeviceSinkBuilder.html), [player API](https://docs.rs/rodio/0.22.2/rodio/struct.Player.html), and [sample-buffer API](https://docs.rs/rodio/0.22.2/rodio/buffer/struct.SamplesBuffer.html) are the versioned output API references.

The A24 owner keeps the device sink and player alive and constructs each decoder module inside its own thread because the module holds a native pointer. A requested track/order travels through a small command channel; the module seeks by order and row zero with readback, and initialized PCM travels through a bounded two-block queue. Order changes discard stale blocks. The app requests play/pause and transition; the decoder owns module lifetime and local music volume. Effects use other players on the same output stream. The original-binding output probe tested continuous two-block scheduling, one 0→12 transition, pause/resume and clean stop for about 2.4 seconds; long-term underrun behavior, loop boundaries and actual-game transitions remain unverified.

`openmpt 0.3.1`'s published `Module::create_from_memory` takes `&mut Vec<u8>` and returns only `Result<Module, ()>`. Its stereo render implementation requests **half the Vec capacity**, not half its length; callers using that older probe must initialize full capacity, bound returned frames, and inspect only that many samples. It does not enforce sample rate or report detailed load errors. The original binding instead renders through the exact provided `&mut [f32]` length, accepts borrowed input bytes, reports native load errors, and validates order/row readback. Neither probe proves decoder safety against malicious modules. Keep the main `unsafe_code = "forbid"`; direct C-symbol FFI in that crate is rejected.

After successful native loader startup, module decoder or output-device failure reports a nonfatal music-unavailable diagnostic and gameplay continues. Missing native DLLs are diagnosed by the launcher before startup. Do not invoke the original executable, silently use a different track, or commit converted proprietary audio. Local conversion to WAV is not selected: it adds generated install-derived files and does not solve startup transitions or loop handling.

## Executed checks and limits

All scripts were parser- and automatic-variable-validated through `Invoke-CodexPowerShell.ps1`; Cargo used ignored, private `CARGO_HOME` and `CARGO_TARGET_DIR`. The first decode probe (`.scratch/audio-probe-01/crate/src/main.rs`) compiled and loaded all three owned MO3 files. It checked order bounds, readback and finite nonzero PCM at `Insaniq2` orders 0/12/25/37, `Alien` 0/1/3 and `Lullaby` 0; invalid bytes returned an error in its focused test. Owned file hashes and exact measurements remain in the ignored probe output. Its first compile failed because the published wrapper requires `&mut Vec<u8>`; corrected and passed.

The second output probe (`.scratch/audio-output-probe-01/crate/src/main.rs`) used only owned `Insaniq2` order 0 then order 12. It rendered two 38,400-frame stereo blocks at 48 kHz, each with 76,800 nonzero finite samples, opened the default device, applied local player gain 0.05, and kept one queued item. Process PID 11224 exited after 989.7891 ms. Position advanced to 325 ms; while paused for 200 ms it changed from 325 to 330 ms; after a bounded stop/drain and order seek the second position reached 295 ms. Output callback errors were zero, the final queue emptied, and the process exited 0. `Player::stop()` is asynchronous: an immediate-empty assertion failed in the first runtime attempt; source review and a bounded drain resolved it. The initial output build had a separate channel-count type error (`NonZero<u16>` required), corrected before the runtime checks. Rodio's expected sink-drop notice appeared at shutdown. No owned probe process remained, and `.scratch/` is ignored.

At this earlier probe stage, the callback count and position proved API progress on this host, not audible fidelity, low-latency reliability, absence of glitches, or exact source mixing. That probe did not perform a loopback capture, sound-device selection or system volume/settings change, full track loop, fade, concurrent effects, actual-game pause/resume, or a normal-speed visible playtest; the later coordinated window results above cover only their stated cases. No original executable, original save or installed file was changed.

The original binding probe used `.scratch/audio-binding-probe-01/run-binding-tests.ps1`, validated and executed through `Invoke-CodexPowerShell.ps1`, with its own `CARGO_HOME`, `CARGO_TARGET_DIR`, import-library search path, and process-local native DLL path. On Rust 1.95.0 MSVC, `cargo test --offline` passed two integration tests: invalid/empty module diagnostics, invalid rate/odd/oversized/zero buffers, bounded slice writes, repeat control, invalid order/row, and all eight requested orders of the three installed MO3 files. Each order returned finite nonzero stereo PCM; `Lullaby` order 0 first became nonzero after 131,072 frames, so the original four-block test failed and was corrected to allow up to thirty bounded blocks. The first crate compile failed on a moved Rust `Option<String>`; a narrow ownership fix resolved it. `cargo fmt --check` and `cargo clippy --offline --all-targets -- -D warnings` then passed in the private crate. No output device was opened for this binding probe, and there was no main-crate build or integration. These checks establish ABI linkage and bounded decoding for the owned files on this host, not continuous playback, malicious-input safety, retail mixing, or fidelity.

The subsequent `.scratch/audio-binding-probe-01/run-output-probe.ps1` was parser/automatic-variable validated before execution. It verified archive SHA-256 `A23E375E576E3A6997FFEEB6CF34488E9020E2A5D8226856B02628B6A87C5E8E` and import library SHA-256 `537758E3D065281E887C0D3310BE471FCB322DE82F74F5DF969624D7A16156CF`, built a new locked/offline `rodio 0.22.2` probe with a private target, verified and copied the five tabled DLLs beside `.scratch/audio-binding-probe-01/output-target/debug/turbofish_audio_binding_output_probe.exe`, and checked their hashes again.
